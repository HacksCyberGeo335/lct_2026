# Стройконтроль: frontend

React + TypeScript (strict) + Vite, React Router, TanStack Query, Motion for React.
Пять разделов: ведомость объектов, площадка, соответствие графику, календарный график и настройки.

## Быстрый запуск

Нужен Node.js **20.19+ в ветке 20 или 22.12+** (локально проверено на 24.20.0), npm.

```sh
cd prom_app/frontend
npm ci
npm run dev
```

Откройте http://127.0.0.1:5173/objects. По умолчанию dev запускается в demo.
Приложение и шрифты работают без внешних сервисов; восемь синтетических роликов входят в репозиторий.

В API-режим можно перейти кнопкой «Подключение API» в верхней панели. Это явный выбор,
ошибки сервера никогда не включают demo. Режим можно закрепить в ссылке
`/objects?mode=demo` или `/objects?mode=api`.

## Конфигурация

При необходимости скопируйте `.env.example` в `.env.local`.

| Переменная                               | Назначение                                                                                       |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `VITE_APP_MODE=demo` либо `api`          | Начальный режим. Без значения: dev = demo, production = api                                      |
| `VITE_API_BASE_URL=/api`                 | Публичный префикс API. Поддержан старый адрес `http://localhost:8080`, к нему добавляется `/api` |
| `API_PROXY_TARGET=http://127.0.0.1:8080` | Только dev-сервер Vite; не попадает в bundle                                                     |

Все `VITE_*` публичны и подставляются **при сборке**. Изменение окружения уже запущенного
nginx не меняет приложение — нужна пересборка. Неизвестный режим показывает ошибку конфигурации.
Параметр ссылки `mode` позволяет явно просмотреть другой режим; он не даёт серверных прав.

Приложение раздаётся из корня домена, Vite base и BrowserRouter basename — `/`.
Размещение в подкаталоге требует согласованного изменения обоих значений и путей локальных медиа/шрифтов.

## Сборка и существующий Compose

```sh
npm run build
npm run preview
```

Preview: http://127.0.0.1:4173/objects?mode=demo. По умолчанию production показывает API.
Preview предназначен для проверки статики, production proxy на нём не проверяется.

Для сборки, которая стартует в demo:

- PowerShell: `$env:VITE_APP_MODE='demo'; npm run build; Remove-Item Env:VITE_APP_MODE`
- bash: `VITE_APP_MODE=demo npm run build`

Из корня репозитория:

```sh
docker compose up -d --build
```

Frontend: http://localhost:3000. Можно собирать только frontend: `docker compose build frontend`.
**Исходный Dockerfile сохранён без изменений** по указанию пользователя. Он использует
`node:20-alpine`, `npm ci`, `npm run build` и nginx. Сборка проверяет типы перед Vite.

В Compose изменено только значение по умолчанию для frontend build arg:
`VITE_API_BASE_URL=/api`. Старое значение из корневого окружения также поддерживается.
При публичной базе `/api` nginx проксирует `/api/` и `/health` в `api_gateway:8080`.
Реальный публичный адрес MinIO приходит из backend; внутренние hostname не переписываются.
Настройте `MINIO_PUBLIC_ENDPOINT` на стороне backend для браузера пользователя.

SPA fallback применяется к маршрутам интерфейса. `/api`, `/api/`, `/assets/`, `/media/`
обрабатываются отдельно и не получают `index.html` вместо ошибки.
JSON access logs frontend сохраняют исходные поля и пишутся в stdout; ошибки — stderr.
Dockerfile, PostgreSQL, MinIO policies, Redis и стек Grafana/Loki/Alloy не менялись.

## Что реально подключено

Проверено по обработчикам ветки `core-back-pipe` и `API-Specification.md`:

1. `GET /health`: проверка Gateway.
2. `POST /api/videos/init-upload`: `{file_name, size}`.
3. Прямой unsigned `PUT` в публичный MinIO.
4. `POST /api/videos/{uuid}/upload-complete`: `{}`, успешный ответ с пустым телом.

DTO проверяется через Zod. Текущий `storage_key` содержит bucket, UUID и basename.
Адаптер удаляет дублирование bucket и кодирует сегменты, включая кириллицу, пробелы, `#`, `+`, `%`.
Полноценный подписанный URL используется без изменения подписи, query и ключа.

Прогресс приходит из `XMLHttpRequest.upload`. После ошибки PUT или отмены complete не вызывается.
После ошибки complete кнопка повторяет только подтверждение. Двойной запуск блокируется,
init не повторяется автоматически после неизвестного сетевого результата.
Сессия повторного подтверждения существует в памяти текущей страницы; после её перезагрузки UUID
нужно сверять с backend вручную, поскольку endpoint чтения/восстановления сессии отсутствует.

Ограничения интерфейса: непустой MP4/WebM/MOV, до 2 ГБ. Это **клиентское ограничение**;
backend проверяет только имя и положительный размер. Совместимость кодеков зависит от браузера.
Отмена не означает удаления строки БД или частично загруженного объекта.

`READY` означает, что файл загружен. **Анализ пока недоступен**: API processing, детекций
и треков в репозитории нет. Объект/камера не отправляются вымышленными полями.
Список загруженных видео и выбор объекта для записи существуют только в текущем сеансе.

## Демосценарий

1. Откройте ведомость, найдите объект по названию, округу или разрешению, задайте статус и порядок.
2. Выберите камеру. Источник «Демовидео» — настоящий локальный WebM (60 секунд);
   «Серия демоснимков» — та же синтетическая схема с выбором времени.
3. Включите рамки и траектории. Цвета классов едины в кадре и сводке. Время видео берётся
   из `currentTime`; лента содержит события только до текущей позиции выбранной камеры.
4. «Сценарий демонстрации» воспроизводит ожидание, обработку, ошибку, успех и пустые детекции.
   Это явный переключатель тестовых состояний, а не таймер успешного распознавания.
5. «Загрузить запись» открывает выбранное видео локально через object URL. Прогресс передачи
   не имитируется, ML-результаты к этому файлу не добавляются. Файл не отправляется в demo.
6. В отчёте выберите 7/14/30 дней, откройте этап и кадр-основание.
7. Импортируйте календарный CSV, измените настройки, перезагрузите страницу и проверьте сохранение.
8. «Печать / сохранить PDF» открывает системную печать. Скачивание PDF автоматически не обещается.

Шесть объектов из референса охватывают норму, риск, отсутствие камер и недостаток данных.
Школа содержит недоступную камеру; у ледового центра нет трекинга; у теннисного центра нет камер.
Счётчик кадра и уникальные треки разделены. Дедупликация между камерами не заявляется.

Срез демоданных: **25.08.2026**, часовой пояс **Europe/Moscow**.
Будущие даты планов не становятся наблюдённым фактом. Готовность в ведомости — отдельная
иллюстративная характеристика объекта. Доли выполнения этапов заданы fixtures;
агрегат взвешен по плановой длительности этапов, соответствие = min(100, факт/план × 100).
Это документированный пример методики, не расчёт физической готовности по числу машин.
График показывает детерминированную иллюстративную историю к тому же конечному агрегату.
Нет наблюдений — нет расчёта, а не ноль.

Планы и настройки: `localStorage` с префиксом `stroykontrol:demo:v1:`, отдельно по объектам.
Сброс в настройках восстанавливает все demo-планы/настройки; API и исходные файлы не затрагивает.
Email/SMS не отправляются. Сотрудники — явно подписанные демонстрационные записи.

## Формат импорта

UTF-8 CSV с запятой или точкой с запятой, BOM допустим. До 2 МБ / 2000 этапов.
Шаблон скачивается с экрана календаря. Колонки сопоставляются в диалоге:

| Колонка        | Содержание                                                        |
| -------------- | ----------------------------------------------------------------- |
| `name`         | Название, обязательно                                             |
| `start`, `end` | Даты ГГГГ-ММ-ДД, обязательно; начало не позже окончания           |
| `id`           | Необязательный уникальный ID; иначе генерируется из номера строки |
| `zone`         | Необязательная зона                                               |
| `equipment`    | `exc`, `dump`, `crane`, `mixer`                                   |
| `quantity`     | Целое неотрицательное число; при указании нужен класс техники     |

Проверяются календарная корректность дат, дубли ID/этапов, числовые значения,
пропуски, количество полей и повторное сопоставление колонок. Параллельные этапы разрешены.
Preview показывает первые 20 строк, валидация охватывает весь файл; ошибки имеют номера строк.
До «Применить план» изменений нет. Применение заменяет demo-план выбранного объекта.
Наблюдения импортированным этапам не выдумываются. В API доступен только preview.
XLSX не поддерживается и не предлагается.

## Проверки

```sh
npm run typecheck
npm run lint
npm run test
npm run build
npx playwright install chromium
npm run test:e2e
```

Vitest + Testing Library проверяют границы и фокус. Playwright проверяет основные сценарии,
reduced motion и размеры 1440/1280/768/390. Скриншоты/PDF: `artifacts/`,
отчёт и traces: `playwright-report/`, `test-results/` (не коммитятся).
Транспорт загрузки в E2E подменяется явно: это не проверка живого MinIO.

`node tools/verify-production.mjs` проверяет собранное приложение через nginx.
Укажите `PRODUCTION_URL` (по умолчанию `http://127.0.0.1:4180`); скрипт требует
production-сборку с начальным режимом api и раздачу с настроенным proxy/fallback.

`node tools/verify-preview.mjs` запускает локальные серверы на свободных портах 4173 и 5174,
проверяет production preview и ошибку неизвестного режима в браузере, затем закрывает серверы.
Перед проверкой выполните `npm run build` без VITE_APP_MODE (начальный production-режим api).

Синтетические видео можно воспроизвести заново: запустите dev-сервер, установите ffmpeg,
затем `node tools/generate-demo-media.mjs`. Генератор пропускает существующие ролики,
снимает SVG-сцену из приложения и кодирует WebM VP9. Чужая съёмка не используется.

Подробности: [проверка результата](../../docs/frontend-verification.md),
[недостающие API](../../docs/frontend-api-gaps.md).
