## 2. Подключённые возможности

Все существующие прикладные HTTP-методы уже были подключены в исходном `main` через
`src/api/videoApi.ts` и `src/api/http.ts`. Новых готовых backend-endpoints, которые можно
было бы дополнительно подключить, не найдено. Клиенты и DTO не дублировались.

Сохранены и проверены: health, последовательная загрузка init → PUT → complete,
реальный прогресс PUT, отмена, повтор подтверждения без повторной передачи,
просмотр по URL объекта текущего неподписанного MinIO-контракта.

Доработано: ручное обновление health и приоритет ошибки над старым успешным ответом;
отдельные loading/error/retry состояния просмотра; показ UUID загруженной записи;
явное объяснение, что READY не является результатом анализа.

## 3. Замена mock-данных

Реальные запросы загрузки и health уже существовали, поэтому новых «замен моков на API» нет.
Mock-реестр/камеры/проценты/настройки нельзя заменить настоящими данными: контрактов нет.
В `main` они удалены из runtime вместо имитации интеграции. Соответствующие маршруты
показывают ограничение backend, рабочую загрузку и список записей текущего сеанса.

Собственные снимки, профиль, CSV и явно импортированный результат работают локально.
Эти действия не выдают себя за серверную обработку. Автоматические тревоги по справочнику
не включались; правила справочника и контракт JSON результата v1 сохранены.

## 4. Что требуется от backend

| Возможность | Чего нет | Что делает frontend сейчас |
| --- | --- | --- |
| Объекты и камеры | Чтение реестра, карточек и камер; реальные ID и права доступа | Показывает отсутствие данных, без вымышленных объектов |
| Список/статус видео | GET списка/карточки, связь с объектом/камерой | Хранит только подтверждённые загрузки текущего сеанса |
| Анализ | Запуск задачи, состояние/ошибка, итоговые детекции, timestamps/координаты/классы, качество | Не запускает обработку, разрешает явно импортировать внешний JSON для своих снимков |
| Календарь/аналитика | API плана и его сохранения, фактического прогресса, доказательств и отчётов | Локальный CSV в проверке снимков; остальные разделы сообщают об отсутствии API |
| Пользователи/уведомления | Auth, роли, сохранение настроек, рассылки | Нет вымышленных сотрудников и обещания отправки писем/SMS |
| Управление загрузками | Удаление/отмена на сервере, очистка UPLOADING, идемпотентность init, resumable upload | Отмена останавливает клиентскую передачу; серверная запись/частичный объект могут остаться |
| Защищённое хранение | Выдача presigned PUT и отдельного GET, политики доступа | Использует текущий публичный URL; PUT-подпись не переиспользуется как разрешение GET |

Конкретные будущие пути/форматы API не придуманы. Их должна предоставить backend-команда.

## 9. Несовпадения и риски интеграции

- `upload_url` указывает на бакет, `storage_key` уже содержит бакет. Существующий адаптер
  собирает URL объекта и кодирует имя; повторять имя бакета нельзя.
- `upload-complete` возвращает пустой 200, поэтому клиент не требует JSON.
- Размер приходит от клиента при init; после HEAD backend сохраняет фактический размер,
  но не сравнивает их и не проверяет кодек/декодируемость. Лимит 2 ГБ — ограничение UI.
- `MINIO_PUBLIC_ENDPOINT` должен быть доступен с машины браузера. HTTPS-frontend с
  HTTP-MinIO получит mixed-content блокировку. MinIO CORS/GET/PUT должны работать отдельно от Gateway CORS.
- Текущая политика MinIO публичная. Auth и защищённые ссылки отсутствуют; frontend
  не должен придумывать или хранить серверные секреты для обхода этого ограничения.
- READY подтверждает завершённую проверку объекта и UPDATE, но не анализ. После потери
  ответа init клиент не знает, создана ли запись; автоматического повтора init нет.
- Статические старые API-документы содержат устаревшие утверждения про отсутствие proxy/
  runtime-валидации. Проверка выполнена по Go-handlers и действующему TypeScript-клиенту.

## Оформление изменений

По разрешению пользователя изменения разделены на два локальных коммита:

1. `main`: «Рабочий frontend: интеграции и отделение демо».
2. `demo`, непосредственно поверх коммита main: «Демонстрационное дополнение приложения».

Общие изменения входят только в коммит main. Коммит demo добавляет демонстрационные
данные, страницы и сценарии к рабочей версии. Исходная точка обеих веток — `e22ae82`.
При оформлении основание demo перенесено на новый main с сохранением рабочих файлов.
Пуш не выполнялся; другие ветки и backend не изменялись.

`CHANGE_STATUS.md` сохраняет исторический список правок до оформления коммитов.
Текущее состояние проверяйте через `git status` / `git log` в соответствующем checkout.
Дальнейшие общие изменения вносите в main и сливайте main в demo. Обратное слияние
вернёт демоданные в рабочую ветку.
