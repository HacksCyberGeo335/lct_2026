# Справочник работ: локальная frontend-интеграция

Ветка `core-back-pipe`. Изменения находятся только в `prom_app/frontend`.
Backend и Dockerfile не меняются. Основание — актуальные JSON из `data_by_gen_ai.zip`,
проверенные в аудите от 22.09.2026; исследовательский текст архива не считается действующим API.

## Запуск и первый сценарий

Из папки этого frontend:

```powershell
npm.cmd ci
npm.cmd run dev
```

Откройте [проверку снимков](http://127.0.0.1:5173/objects/north-park/inspection?mode=demo)
и нажмите **«Открыть пример со справочником»**.
Сервер, Docker и ML для этого сценария не нужны.

1. Выбрана работа `work_047`, «Устройство котлована», зона **А** (кириллица),
   август 2026. Это заданный демонстрационный план, не вывод модели из изображения.
2. Экскаватор виден; грунт складируется на площадке. Группа самосвала
   показывает **«Условие не применяется»**.
3. В поле «Перемещение грунта» выберите **«Вывоз самосвалами»**.
   Для первого снимка появится **«Не обнаружено в наблюдениях»**:
   один кадр не доказывает отсутствие машины на площадке.
4. Выберите `pit-ok.png`: появится связанный класс самосвала.
   Это не подтверждает выполнение функции или готовность этапа.
5. Снимите фазу «Вывоз грунта»: требование станет неактивным.
   Оставьте метод неизвестным: интерфейс запросит контекст.
6. Откройте карточку работы: возможная техника, наблюдаемость, длительности,
   источники и условные зависимости доступны отдельно.

Четыре изображения и их результаты синтетические. При замене непустого сеанса
примером требуется подтверждение. Старый количественный сценарий доступен через
**«По ресурсному плану · демо»** или `?mode=demo&rules=legacy`.
Его числа и предупреждения не являются правилами нового справочника.

## Собственные файлы

1. Выберите объект и работу по ID, контексту или названию. Задайте независимый
   план оператором либо выберите строку календаря.
2. Укажите метод, активные фазы и допустимые для проекта альтернативы.
3. Добавьте PNG/JPEG/WebP. Импортируйте совпадающий JSON v1 распознавания,
   проверьте preview и примените. Формат: [ANALYSIS_CONTRACT.md](ANALYSIS_CONTRACT.md).
4. В «Камера и возможности модели» задайте точные `camera_id` и `model`
   из результата, обзор, реально поддерживаемые классы и согласованный порог.
   Подтвердите проверку этих настроек. Профиль другой камеры/модели не применяется.
5. Читайте объяснения каждой группы. «Скачать объяснение проверки» экспортирует
   профиль, версии, состояния, основания и исходные результаты с хешами снимков.

Импорт JSON не запускает ML; файл не подтверждает достоверность времени,
места или распознавания. Совпадение SHA-256/имени/геометрии защищает от
привязки к другому изображению, а не от ошибочного содержимого результата.
Изображения и JSON остаются в памяти вкладки до перезагрузки, смены режима
или сброса. Рамки показывают все детекции; таблица отображает текущий порог проверки.

## План, профиль и совместимость

Карточка справочника и строка плана — разные сущности. Повторная работа в другой
зоне или в другой период имеет отдельный ID строки, хотя `work_id` совпадает.
Для CSV добавлены необязательные парные колонки `work_id` и `catalog_id`.
[Пример](public/catalog/plan-example.csv) ссылается на
`construction-reviewed-2026-09-18`. Старые CSV, иерархия `parent_id` и
явные ресурсы остаются совместимыми. Ресурсная политика не подмешивается
в функциональные группы. Даты и родители не выводятся из порядка карточек.

Импорт на странице снимков заменяет план **сеанса**, не календарь объекта.
В календаре импорт сохраняет план demo-объекта. Неизвестная работа/версия
в новом сценарии даёт ошибку. При изменении связанного плана необходимо
заново выбрать строку. Сводные строки и AGGREGATE не запускают проверку.
Для старой строки без привязки можно явно выбрать карточку вручную.

Профиль — отдельный локальный JSON `version: 1`. Он содержит:

- `siteId`, `catalogId`, `workId`; источник плана, `stageId`, зону и даты;
- условия, активные фазы, альтернативы по `requirement_id`;
- камеру, модель, поддерживаемые классы, порог уверенности и обзор;
- одиночный/интервальный режим, границы интервала, минимум моментов и максимум перерыва;
- метку `draft` или `demo` — ни одна не означает инженерное утверждение.

«Сохранить профиль в браузере» и экспорт выполняются явно. Хранение разделено
по demo/API и объектам; импорт проверяет версию, объект, даты и все ссылки,
показывает preview до замены. При несовместимом сохранённом профиле видна ошибка;
он не удаляется автоматически. Снимки и импортированный план сеанса в профиль
не входят: их нужно открыть повторно после перезагрузки. Один объект хранит один
текущий профиль; несколько вариантов можно сохранить отдельными JSON-файлами.
Сброс demo в настройках удаляет и demo-профили.

Результат распознавания v1 остаётся входным форматом без выдуманного нового API.
Проектный контекст поступает **отдельно от распознавания**, через профиль/план.
Экспорт объяснения v1 связывает их для локального воспроизведения. Серверный
контракт контекста, авторизация и статусы согласования требуют решения команды.

## Проверка групп и интервала

Применимые функциональные группы проверяются независимо (AND). Внутри группы
достаточно одной совместимой альтернативы (OR); одна физическая машина может
относиться к нескольким функциям. Количественные нормы из справочника не выводятся.
Все списки альтернатив открытые и требуют проектного выбора.

Неизвестный метод → недостаточно данных; явно другое условие → не применяется;
невыбранная фаза → неактивна. Возможная техника не становится обязательной.
Неописанный класс не считается нарушением. Уверенная подходящая детекция
сохраняет значение наблюдения даже при постороннем неизвестном классе.
Низкая уверенность подходящего класса и недоступные детектору альтернативы
мешают заключать об отсутствии наблюдения. Общий `crane` не доказывает оснастку.

В интервале задаются камера, зона, московские границы, минимум **различных
моментов** и допустимый перерыв. Значений по умолчанию для этих порогов нет.
Проверяются крайние промежутки и разрывы между моментами, качество/состояние
результатов, совпадение модели и плановых дат. Кадры разных камер не объединяются,
число машин между кадрами не складывается. Нет метаданных у снимка — нет основания
включить его в интервал. Локальный набор не доказывает полноту серверного потока.

**Во всех 377 исходных карточках автоматическая тревога отсутствия отключена.**
Настройки оператора этот флаг не меняют. Даже достаточно покрытый интервал
даёт наблюдение, не подтверждённое нарушение/риск. Нет автоматического
процента готовности, индекса риска, оценки сроков или распознавания стадии.

## Данные, версии и происхождение

Загружаются три неизменённых файла из архива: cards 3.1-reviewed, equipment 1.1,
duration review 1.0. [Манифест](public/catalog/manifest.json) фиксирует размер
и SHA-256 каждого. Проверяются схемы, ID, ссылки, классы и согласованность;
повреждённый набор не применяется частично. Загрузка отложена до открытия
нового раздела снимков, результат индексируется и кешируется.

377 карточек (329 ITEM / 48 AGGREGATE), 127 видов оборудования, 18 классов
детектора, 175 групп. Словарь детектора не доказывает возможности реальной модели.
Адаптер `legacy-demo-to-catalog-1` переводит старые демонстрационные ID:
`exc → excavator`, `dump → dump_truck`, `dozer → bulldozer`,
`mixer → concrete_mixer_truck`, `mobile_crane/manipulator → crane`.
Семантика `mixer` здесь — автобетоносмеситель прежнего демо; стационарный
смеситель нельзя так маркировать. Исходные ID и результаты сохраняются.

66 примеров длительности связаны со 134 работами; у 243 числового ориентира нет.
Единицы, диапазон, основание, ресурсы, формула, ограничения и источник показаны
без пересчёта в календарные даты. Частичный пример не является сроком всего этапа,
статистически подтверждённых средних в наборе нет. Формулы отображаются как текст.
Reviewed — документарная проверка составителем, не утверждённый ППР.
Внешние нормы повторно не проверялись. Исторические JSON/XLSX в приложение не включены.

## Что остаётся командной задачей

Frontend готов к локальной работе с имеющимися данными. Для живой системы нужны
API снимков/планов/результатов, реальные классы и качество ML, достоверные зоны
и метаданные, инженерное согласование альтернатив и временных критериев.
Включение автоматических тревог, классификация стадии и индекс риска требуют
отдельной версии правил и согласованного контракта. Они не имитируются этим демо.

Проверки: `npm run typecheck`, `npm run lint`, `npm test`,
`npm run test:e2e`, `npm run build`, `node tools/verify-preview.mjs`.
Для проверки готовой nginx-раздачи: `PRODUCTION_URL` и
`node tools/verify-production.mjs`. Dockerfile сохранён.
